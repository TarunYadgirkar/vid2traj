Turn demonstration video into robot trajectories

vid2traj reads ordinary RGB video, estimates the wrist pose in every frame, and retargets it onto a specific robot without leaving its joint, speed, or collision limits. The output is a LeRobot dataset you can train on.

What these numbers do not cover

  • Real footage. Every measured number on this page comes from the marker path on synthetic clips.
  • Metric scale from one uninstrumented camera. The marker frontend is metric because the marker size is known; the hand frontend estimates scale from a nominal hand size.
  • Contact. Nothing models forces or dynamics, so a grasp that looks right kinematically may not hold an object.
  • Multiple cameras and on-robot execution. Both are out of scope for now.

Why convert video at all

Imitation learning needs hours of demonstrations. Today that usually means a teleoperation rig: an operator, a leader arm, a follower arm, and the robot itself, before you have any data.

Video of people doing tasks with their hands is easy to record by comparison. A video is not a trajectory, though. It has no joint angles, no metric scale, no idea what a particular arm can reach, and no guarantee that any of it is safe to execute.

vid2traj covers that gap end to end. It estimates the wrist pose per frame, lifts it into a world frame, smooths it, solves inverse kinematics against a real robot model, and refuses to emit any pose the robot could not safely hold. The result loads directly into the LeRobot training stack.

How it works

Six stages, each consuming the previous one's output. Every image below came out of a real run on the synthetic clip.

  1. 01

    Read the video

    Frames go in one at a time. No depth channel is assumed, and nothing beyond the camera intrinsics needs calibrating.

  2. 02

    Estimate the wrist pose

    Two interchangeable frontends sit behind one interface. An ArUco marker gives a metric, deterministic reading and produced every number on this page. MediaPipe Hands tracks bare hands on a CPU in real time, but it has not been validated on real footage yet. A frame with no confident detection returns nothing rather than a guess.

  3. 03

    Lift to the world, then smooth

    The camera extrinsic puts every pose in one fixed frame. Short dropouts are interpolated. Long ones are flagged and left unfilled, because a smooth line through a gap nobody observed would be invented data.

  4. 04

    Retarget onto the robot

    A fixed wrist-to-gripper offset from the robot's config turns the tracked pose into a target pose. Damped least-squares IK on MuJoCo's analytic Jacobian then solves for joint angles. Redundant arms get a null-space pull toward the home pose, so the elbow stays put instead of flipping between solutions.

  5. 05

    Refuse anything unsafe

    Every candidate pose is clamped into the joint limits, rate-limited so no velocity or acceleration limit breaks, and checked for self-collision in MuJoCo. If a pose still fails, the previous valid one is held and the frame is recorded as held.

    Order matters here. Rate-limiting before the collision check lets the arm refuse a bad pose without an acceleration spike as it stops.

  6. 06

    Export as a LeRobot dataset

    Parquet plus MP4 in the v3.0 layout, with the metadata the real loader expects. Two runs on the same input produce byte-identical files.

    meta/info.json meta/tasks.parquet meta/episodes/chunk-000/… data/chunk-000/file-000.parquet videos/observation.images.side/…

How the claims are tested

The core regression generates a known joint trajectory, renders it to video, runs the whole pipeline on that render, and compares the recovered end-effector pose with the trajectory it started from. Nothing in between is mocked.

When a frame cannot be solved

There are two kinds of failure, marked differently. A pose the safety pass rejects (self-collision that survives rate limiting) falls back to the last pose it trusts; the review page marks it amber and the safety report counts it as held. A frame perception never saw is marked unobserved instead: short gaps are interpolated, and long ones hold the last solved pose. Either way the robot pauses rather than lunges.

Adding a robot takes one config file

Nothing in the retargeting, safety, or export layers branches on which robot it drives. The model path, joints, limits, home pose, wrist offset, gripper mapping, and IK gains all live in YAML.

SO-101 is the harder case on purpose. Five joints cannot reach an arbitrary 6-DOF pose, so its config marks orientation as a soft preference and convergence is judged on position alone. That is a flag in the file, not a branch in the code.

Run it

Needs Python 3.10 or newer and ffmpeg on your PATH. The synthetic clip comes with its ground truth, so you can reproduce the numbers above.

# install
pip install -e .

# render a synthetic clip with known ground truth
vid2traj synth --out demo/

# convert it into a LeRobot dataset for the Franka Panda
vid2traj convert demo/clip.mp4 --embodiment franka_panda \
  --camera demo/camera.json --out demo/dataset

# build the side-by-side review page
vid2traj viz demo/dataset --video demo/clip.mp4 --out review.html
